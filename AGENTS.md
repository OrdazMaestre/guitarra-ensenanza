# Project workflow rules

- Public pages must be fully responsive on the X axis. Do not leave horizontal overflow on desktop or mobile; prefer fluid widths, `minmax(0, ...)`, and `max-width: 100%`.
- Lesson pages with previous/next navigation must leave clear vertical breathing room between the page content and the pager links. Prefer the shared `TemarioPager` spacing instead of one-off page margins.
- Lesson copy for children should use short, separated sentences whenever practical. Prefer several brief lines or paragraphs over long multi-sentence paragraphs.
- In fretboard note maps, red is reserved for one concrete note that the current lesson intentionally marks as special, such as a blue note or a chord seventh. Do not use red for ordinary notes inside a full scale; keep only the major and minor tonics highlighted unless the lesson explicitly teaches another special note.
- Secret links must be truly indistinguishable from the ordinary element they replace. They must not show link styling, animation, hover color, focus outline, extra spacing, layout shifts, tooltip-like text, or a pointer cursor. If the normal surrounding UI changes the mouse cursor on hover, the secret link should deliberately keep the normal cursor so the hidden target feels like an easter egg, not a visible control.
- When adding a new lesson page, extension page, practice page, or any new route that branches from the temario, update `/lecciones/temario/pasos` in the same change so the visual tree stays true to the real navigation paths. Main sequence changes belong in `app/lecciones/temario/temarioData.ts`; side branches belong in `branchMap` inside `app/lecciones/temario/pasos/page.tsx`.
- Horizontal AlphaTab tablatures must use the player's own top scrollbar. Do not wrap `AlphaTabPlayer` in an external `overflow-x: auto` container or force min-width on that wrapper; it creates a second bottom scrollbar and breaks playback-following. If a horizontal tablature needs more space or must show the scrollbar, pass `horizontalBarWidth` to `AlphaTabPlayer`.
- When reporting work on a page, always include a direct browser link to the page being reviewed so it can be opened in Google Chrome with one click.
- Every MIDI instrument (interactive fretboard or keyboard) must include an individual volume slider. Use `const [volume, setVolume] = useState(1.0)`, pass `volume` to every `playNote` and `switchNote` call, and render a slider UI matching the existing pattern (green accent `#047857`, width 112 px, step 0.05, label showing `Vol {Math.round(volume * 100)}`). This applies to all future instruments as well.
- Every MIDI instrument must also include a keyboard-input toggle button (`KB` / `KB: ON`). Use `const [kbMode, setKbMode] = useState(false)` and add a `useEffect` on `kbMode` that registers `window` `keydown`/`keyup` listeners using `e.code` (not `e.key`) to be layout-independent. Fretboards use `FRETBOARD_KEYMAP` from `@/app/lib/fretboardKeymap`; keyboards define their own map. Always call `e.preventDefault()` inside the keydown handler. Render the KB button in the same flex row as the volume slider.
- Interactive fretboards implement hammer-on / pull-off / tapping with three refs and one state: `kbKeysHeldRef = useRef(new Map<string, {string, fret, midi}>())` (all physically held keys), `kbStringVoiceRef = useRef(new Map<number, {code, voiceId}>())` (one active voice per string number), `volumeRef = useRef(volume)` kept in sync via `useEffect`, and `const [kbPositions, setKbPositions] = useState<{string, fret}[]>([])` for visual overlay. Polyphony is capped at 3 simultaneous strings. On keydown: if the string already has an active voice and the new fret is higher, call `switchNote()` (hammer-on); if no active voice exists and the cap is not reached, call `playNote()`. On keyup: if the released key was the active voice, find the highest-fret still-held key on that string and `switchNote()` to it (pull-off), or `releaseNote()` if none remain. After every `await playNote/switchNote`, verify `kbStringVoiceRef.current.get(string)?.code === e.code` before committing the new voiceId (race-condition guard). `interactionOverlay()` reads `const posList = kbMode ? kbPositions : (pressedPos ? [pressedPos] : [])` and maps over it to render one `<g key={\`ko-${string}-${fret}\`}>` per active position. MiniKeyboard uses the simpler `kbVoiceMapRef = useRef(new Map<string, number>())` pattern (no per-string logic needed for a piano layout).
