# Project workflow rules

- Public pages must be fully responsive on the X axis. Do not leave horizontal overflow on desktop or mobile; prefer fluid widths, `minmax(0, ...)`, and `max-width: 100%`.
- Lesson pages with previous/next navigation must leave clear vertical breathing room between the page content and the pager links. Prefer the shared `TemarioPager` spacing instead of one-off page margins.
- Lesson copy for children should use short, separated sentences whenever practical. Prefer several brief lines or paragraphs over long multi-sentence paragraphs.
- In fretboard note maps, red is reserved for one concrete note that the current lesson intentionally marks as special, such as a blue note or a chord seventh. Do not use red for ordinary notes inside a full scale; keep only the major and minor tonics highlighted unless the lesson explicitly teaches another special note.
- Secret links must be truly indistinguishable from the ordinary element they replace. They must not show link styling, animation, hover color, focus outline, extra spacing, layout shifts, tooltip-like text, or a pointer cursor. If the normal surrounding UI changes the mouse cursor on hover, the secret link should deliberately keep the normal cursor so the hidden target feels like an easter egg, not a visible control.
- When adding a new lesson page, extension page, practice page, or any new route that branches from the temario, update `/lecciones/temario/pasos` in the same change so the visual tree stays true to the real navigation paths. Main sequence changes belong in `app/lecciones/temario/temarioData.ts`; side branches belong in `extensionPages`, also in `app/lecciones/temario/temarioData.ts` — `branchMap` lives in `app/lecciones/temario/temarioTree.ts`, derived from that list, so `pasos/page.tsx` never needs editing directly for a new branch.
- The `app/lecciones/temario/[slug]/page.tsx` route is statically prerendered (`dynamicParams = false` + `generateStaticParams()` reading `lessonRouteSlugs` from `temarioData.ts`) to keep it Vercel-compatible. Any new slug handled inside that `[slug]` page (a new `if (slug === ...)` branch, or a new entry in `lessonBlocks`) must also be added to `lessonRouteSlugs` (via `extensionLessonSlugs`, `legacyLessonSlugs`, or `lessonBlocks` itself) in the same change, or the route will 404 at runtime. This does not apply to lessons that live in their own physical folder (e.g. `el-sonido-en-la-musica`, `mas-punteos-cortos`) — only to slugs routed through `[slug]`.
- Every AlphaTab tablature on the site uses `layout="horizontal"` (site-wide decision, 2026-10-04 — no vertical/`page` tablatures). The player's default format (lookahead audio scheduler, "Seguir la tablatura" button turned on by Play, measured string labels, hidden whammy/floyd effects, strings 1–2 at 59.5%/70%, dark-green notation via `notationColor` default `#064e3b`, audible BENDS + tied notes sustained without re-plucking via the shared pure `app/lib/bendCurve.ts` (pitch on `detune`, never `playbackRate`; whammy ignored; also used by Riff-Hero's background notes, sound only — scoring stays by fret; see "Bends y ligaduras" in NOTES and `tests/bend-*.spec.ts`), and the green rounded `.alphatab-frame` style in `globals.css`) applies automatically; don't re-pass those as props on new pages. `legacyPlayback` exists only as an escape hatch. See "Nuevo formato en toda la web" in `app/components/guitar/AlphaTabPlayer.NOTES.md`.
- Horizontal AlphaTab tablatures must use the player's own top scrollbar. Do not wrap `AlphaTabPlayer` in an external `overflow-x: auto` container or force min-width on that wrapper; it creates a second bottom scrollbar and breaks playback-following. If a horizontal tablature needs more space or must show the scrollbar, pass `horizontalBarWidth` to `AlphaTabPlayer`.
- When reporting work on a page, always include a direct browser link to the page being reviewed so it can be opened in Google Chrome with one click.
- Every MIDI instrument (interactive fretboard or keyboard) must include an individual volume slider. Use `const [volume, setVolume] = useState(1.0)`, pass `volume` to every `playNote` and `switchNote` call, and render a slider UI matching the existing pattern (green accent `#047857`, width 112 px, step 0.05, label showing `Vol {Math.round(volume * 100)}`). This applies to all future instruments as well. Peak gain constants across instrument types are NOT directly comparable — MiniKeyboard's oscillator (`startOscillatorVoice` in `guitarAudioEngine.ts`, peak `0.19`) sustains at full level for as long as a key is held, while the guitar's sample voice (`startSampleVoice`, peak `0.52`) decays immediately after the pluck, so equal peak gain made the keyboard measurably louder in practice (confirmed by rendering both offline and comparing RMS, `tests/keyboard-audio-loudness.spec.ts`). If either voice's gain or filter chain changes, re-run that test rather than assuming a peak-gain match is a loudness match.
- Guitar TONE and loudness (site-wide revision 2026-11-02, with guitar-music-advisor + alphatab-guardian; full rationale and measured numbers in the "TONO DE GUITARRA" block of `app/lib/guitarAudioEngine.ts` and "Tono clean y sonoridad" in `AlphaTabPlayer.NOTES.md`). Every CLEAN guitar note goes through `createCleanToneChain` (LINEAR on purpose: just -1 dB at 1.7 kHz + a level trim; a body boost + low-register exciter made the clean lows sound saturated, almost overdriven, so the user had them removed, 2026-11-02 — never add saturation to the clean) and `guitarSampleTrim` (per-sample leveling). That covers `startSampleVoice`, `scheduleGuideNote` and the tab player's clean branch, which builds its own chain per player and must never put that shared node in a voice's `nodes`. Overdrive (`createOverdriveChain`) was retuned (approved by ear) to about clean's loudness with tame 2-5 kHz. In Web Audio, `lowpass`/`highpass` `Q` is in dB: flat/Butterworth = `-3.01`; the first overdrive's "Q 0.7" lowpasses were really a +5 dB 2-4 kHz plateau. Compare loudness in LUFS, never by peak or plain RMS: `tests/helpers/guitarTone.js` (inject with `page.addInitScript`) has a BS.1770 meter, laptop/phone speaker models and EXACT replicas of both chains plus `guitarSampleTrim`; change them together with the engine. Tests: `tests/guitar-clean-tone.spec.ts` (linearity, never brighter than the old raw path on any speaker, peak ≤ 0.84) and `tests/guitar-overdrive.spec.ts` (fretboard and tab player).
- The metronome has its own volume, independent of the instrument's: `useMetronome()` (no longer takes a `volumeRef` argument — every call site was updated) owns `metroVolume`/`setMetroVolume` (`MetronomeAPI`, default `0.5`) and passes `metroVolumeRef.current * 2` as `playMetronomeClick`'s `volume` arg, so 50% reproduces the click's historical loudness and 100% doubles it. `MetronomeControls` renders its slider as a third row in the dropdown, directly below the bpm slider (same visual pattern: green accent, 112px, step 0.05, `aria-label="Volumen del metrónomo"`). Doubling naively would clip: the "kick" click type sums 3 simultaneous layers to a ~0.58 peak at the old default, so 2x reaches ~1.16. Every metronome layer (all types) therefore connects to `getMetronomeLimiter()` in `guitarAudioEngine.ts` — a `DynamicsCompressorNode` dedicated to the metronome bus (never touches guitar/keyboard note voices) — instead of straight to master. Its threshold (-3dB ≈ 0.708) sits above every click type's old-default peak on purpose, so it stays fully transparent at and below 50% and only engages while pushing past it; ratio 20 keeps the doubled kick peak around 0.73, safely under full scale. If click gains, the limiter, or the `* 2` factor change, re-run `tests/metronome-volume-safety.spec.ts` (offline-renders the exact DSP graph and checks both "unchanged at the old default" and "no clipping at the new max").
- Every MIDI instrument must also include a keyboard-input toggle button (`KB` / `KB: ON`). Use `const [kbMode, setKbMode] = useState(false)` and add a `useEffect` on `kbMode` that registers `window` `keydown`/`keyup` listeners using `e.code` (not `e.key`) to be layout-independent. Fretboards use `FRETBOARD_KEYMAP` from `@/app/lib/fretboardKeymap`; keyboards define their own map. Always call `e.preventDefault()` inside the keydown handler. Render the KB button inside the shared `MidiInstrumentChrome` `buttons` slot (see below). Its visible content is an ICON (user request, 2026-10-24: save space): render `<KeyboardToggleLabel />` from `@/app/components/guitar/InstrumentIcons` (computer-keyboard icon + visually hidden "KEYBOARD", so the accessible name and the tests stay the same); likewise `HandednessToggleButton` shows a right/left hand icon (`HandIcon`) instead of "DIESTRO"/"ZURDO", with the text in `aria-label`/`title`. The KB `<button>` must carry `className="midi-kb-toggle"`: on touch-only screens (`@media (hover: none) and (pointer: coarse)` in `globals.css`) it is hidden, together with its `.midi-anchor` wrapper via `:has()`, since there's no physical keyboard to use and it only makes the bar wrap. `playwright.config.ts` enables `hasTouch` globally, which matches that media query, so any spec that clicks KEYBOARD needs `test.use({ hasTouch: false })`.

On wide screens the bar keeps floating and never pushes content (keeping related blocks in view together); on narrow/mobile screens it takes its own space and pushes content down, because covering something important is never acceptable. Don't add per-page breakpoints for this; `tests/midi-floating-chrome.spec.ts` checks both sides (no `is-in-flow` at 1280px; no pill covering other content at 360/600/850px). `children` is a single row rendered in DOM order — always `KB button, volume slider, MetronomeControls` (volume sits *between* the two buttons; this is a deliberate layout choice, not incidental order) — inside one `.midi-float-pill` that wraps onto extra lines (`flex-wrap: wrap`, centered) if it doesn't fit at narrow widths. If the instrument's own `<svg>` sits inside another element that needs `overflow-x: auto` for its own reasons (e.g. `FullFretboardDiagram`'s `.fretboard-wrap`, whose board has a `min-width` forcing horizontal scroll on mobile), `midi-instrument-host` must wrap that scrolling element from the *outside*, with `<MidiInstrumentChrome>` as its sibling — never nested inside the `overflow-x: auto` container, or the floats get clipped/scoped to that scrollbar instead of floating freely. - Physical-keyboard chords on non-gaming keyboards can silently fail to register a 3rd simultaneous key due to real hardware rollover/ghosting limitations — the browser never even receives that key's `keydown`, so no amount of application code can detect or work around it (confirmed by dispatching synthetic 3-key-at-once events via Playwright/CDP: the exact same code correctly plays and sustains all 3 notes when the browser actually delivers the events). Every `kbMode` instrument must therefore show a small warning span (same styling: `fontSize: '11px', color: '#92400e', background: '#fef3c7', border: '1px solid #f59e0b'`, text `⚠ Necesitas teclado gaming para tocar ciertos acordes`) once 2+ physical keys are simultaneously held, using a `const [kbGhostWarn, setKbGhostWarn] = useState(false)` set on every keydown/keyup (and cleared on `kbMode` cleanup). Fretboards additionally narrow this with `hasKeyboardGhosting()` from `@/app/lib/fretboardKeymap` (flags when 2 held keys share the same fret/column, the fretboard-specific risk pattern); MiniKeyboard has no such column concept (its keymap is a 2-row zig-zag of white/black keys) so it simply warns at 2+ held keys.
- Interactive fretboards implement hammer-on / pull-off / tapping with three refs and one state: `kbKeysHeldRef = useRef(new Map<string, {string, fret, midi}>())` (all physically held keys), `kbStringVoiceRef = useRef(new Map<number, {code, voiceId}>())` (one active voice per string number), `volumeRef = useRef(volume)` kept in sync via `useEffect`, and `const [kbPositions, setKbPositions] = useState<{string, fret}[]>([])` for visual overlay. Polyphony is capped at 3 simultaneous strings. On keydown: if the string already has an active voice and the new fret is higher, call `switchNote()` (hammer-on); if no active voice exists and the cap is not reached, call `playNote()`. On keyup: if the released key was the active voice, find the highest-fret still-held key on that string and `switchNote()` to it (pull-off), or `releaseNote()` if none remain. After every `await playNote/switchNote`, verify `kbStringVoiceRef.current.get(string)?.code === e.code` before committing the new voiceId (race-condition guard). `interactionOverlay()` reads `const posList = kbMode ? kbPositions : (pressedPos ? [pressedPos] : [])` and maps over it to render one `<g key={\`ko-${string}-${fret}\`}>` per active position. MiniKeyboard uses the simpler `kbVoiceMapRef = useRef(new Map<string, number>())` pattern for physical-keyboard input (`kbMode`, no per-string logic needed for a piano layout). `KB_KEYMAP` covers two simultaneous, independently-playable registers (like two hands on a piano), neither drawn on the visible C-C SVG octave — same as the pre-existing invisible B(59)/C#-E(73-76) notes: "grave" (bass) is the bottom-row-naturals + home-row-sharps layout, extended by `ShiftRight`/`Enter` for one more natural+sharp pair (F=77, F#=78), mirroring how `FRETBOARD_KEYMAP` uses `ShiftRight`/`Enter` to extend a string by one fret; "agudo" (treble) uses the Q-row (`KeyQ`..`Backslash`, 13 keys) for naturals and the digit row for sharps, positioned between the two naturals each sits above (`Digit2` between Q/W, etc.), skipping `Digit1`/`Digit4`/`Digit8`/`Minus` (no black key between E-F or B-C) and using `Backspace` for the last natural pair's sharp since no digit-row key aligns past `Equal`. Agudo's first 4 naturals (Q/W/E/R) are a deliberate pitch-for-pitch overlap with grave's last 4 (Comma/Period/Slash/ShiftRight) — same MIDI notes, different physical keys — so the two rows read as one continuous scale instead of jumping an extra octave; from there agudo keeps climbing to A6 (93). If this mapping changes again, `tests/mini-keyboard-range.spec.ts` has a visual regression check (`Q` and `Comma` must highlight the same visible key) and `tests/keyboard-audio-loudness.spec.ts` checks the new top note doesn't clip. Independently of that, MiniKeyboard's mouse/touch input on the SVG (not `kbMode`) uses `ptVoicesRef = useRef(new Map<number, {midi, voiceId}>())` keyed by `e.pointerId`, mirroring the fretboard's pointer-touch fix (`ptHeldRef`/`ptStringVoiceRef`) but with a single map, since a piano key has no per-string "one voice" constraint — each simultaneously held pointer/finger is fully independent, capped at `MAX_TOUCH_VOICES = 3`.
- Every fretboard's `interactionOverlay()` (the vibrating orange marker at a pressed string/fret) must render the note name inside the circle: a `<text>` sibling right after the `<circle>` in the same `<g>` (so it inherits the `fretboard-string-vibrate` animation and moves with it), `fill="#b45309"` (a darker amber than the `#fbbf24` circle fill, on purpose — readable without contrasting so hard it steals attention), `textAnchor="middle"`, `y={markerY + 4}` to vertically center on the marker, and `fontSize` scaled to the circle's own radius (`~12` for `r=16`, `13` for `r=17`, `10` for the small `r=12` mini-crop circles in `AcordesSeptimaPage`). The note name comes from `chromaticNotes[(open + fret) % 12]` (`chromaticNotes = ['C','C#','D','D#','E','F','F#','G','G#','A','A#','B']`), where `open` is the open string's pitch class — either an existing page-local `noteNameForFret(open, fret)` + `stringTunings[string - 1].open` (already present in `EscalaCompletaSolMayorPage`, `AcordesSeptimaPage`, `AcordesEscalaSolMayorPage`, `PentatonicaBluesPage`, `PentatonicaPage`) or, where no such helper existed yet (`FigurasAcordesPage`, `NotacionMusicalPage`, `ReducedFretboardDiagram`), a local `noteNameForFret(string, fret)` built from the file's own `OPEN_STRING_MIDI` map. Reuse whichever helper/shape already exists in that file rather than introducing a second `chromaticNotes` array in the same module scope (TS will flag the redeclare).
- MiniKeyboard's physical-keyboard input (`kbMode` only — mouse/touch always keeps the plain full-key fill, via `ptPressedMidis`) highlights a *slice* of a key instead of the whole thing, because a played note's octave often doesn't match the one (or, for C, two) octave(s) actually drawn: `noteOctave(midi) = Math.floor(midi / 12) - 1` maps to a `KbZone` via `kbZoneForOctave` — octave ≤3 → `'bottom-edge'`, 4 → `'bottom-half'`, 5 → `'top-half'`, ≥6 → `'top-edge'` — and `nearestRectMidi()` finds which drawn key (by matching `midi % 12`, nearest by distance when a note name is drawn twice) to render it on. `kbZones: Map<number, Set<KbZone>>` (rect midi → active zones, rebuilt in `syncPressedMidis()` alongside `ptPressedMidis`) lets multiple physical keys mapping to different octaves of the same drawn key show simultaneously (e.g. holding both `KeyM` and `IntlBackslash`, both "B", lights bottom-half green and bottom-edge amber together). Rendered as a `<g data-testid="kb-zones">` of overlay `<rect>`s (half = `#b8e8c4` at 0.9 opacity, spanning half the key's height from its own top or bottom; edge = `#fbbf24`, a thin ~14%-height strip) inserted after the key-fill groups but before the label groups so text stays legible on top. `tests/mini-keyboard-octave-zones.spec.ts` locks in the exact zone/key mapping for the B and C examples that motivated this. C is drawn twice (both ends of the visible octave), so it's the one deliberate exception shared by BOTH input methods: `cSibling(rectMidi)` returns the *other* C key + its own fixed zone (left/`C_LEFT_MIDI`=60 → `'bottom-half'` on the right one; right/`C_RIGHT_MIDI`=72 → `'top-half'` on the left one), and `syncPressedMidis()` calls it for every currently-held kb note AND for every pointer-pressed note in `pt` — so clicking/touching either C still gives that key its own normal full-key fill via `ptPressedMidis` (unchanged), but ALSO adds the sympathetic zone overlay to its sibling, reinforcing that both keys are "the same note" an octave apart. See `tests/mini-keyboard-c-sibling.spec.ts`.
- Every horizontally-scrolling fretboard/chord diagram must offer its own drag-to-scroll bar via the shared `<HorizontalScrollbar targetRef={scrollRef} />` from `@/app/components/guitar/HorizontalScrollbar`, instead of relying on the native scrollbar or on swipe-to-scroll over the diagram itself. Two compounding problems make this necessary, not just one: Android Chrome's native touch scrollbar is a thin overlay that only flashes during an active drag and cannot be restyled into a persistently visible bar (`::-webkit-scrollbar` and `scrollbar-color`/`scrollbar-width` are both ignored on touch overflow containers on Android) — but more importantly, every fretboard's own `<svg>` sets `touchAction: 'none'` plus `setPointerCapture` to support hammer-on/pull-off note input (see the interactive-fretboards rule above), which swallows *every* touch gesture over the diagram, so even swiping the board directly never reaches the browser's scroll handling at all. An earlier attempt at ◀/▶ tap-to-scroll buttons (`ScrollArrows`, since removed) also turned out unreliable on real Android devices — it drove scrolling via `el.scrollBy({ behavior: 'smooth' })` from a plain `onClick`, which has no confirmation and can silently no-op near a `touch-action: none` sibling. `HorizontalScrollbar` instead sets `el.scrollLeft` directly from real pointer events on its own track (`onPointerDown` jumps to that position and calls `setPointerCapture`; `onPointerMove` for the same `pointerId` keeps following; `onPointerUp`/`onPointerCancel` release capture) — the same `setPointerCapture`-driven pattern already proven reliable for touch by the fretboards' own note-input handlers, so it never depends on the browser's scroll-animation queue or native scrollbar rendering. It measures the target's `scrollLeft`/`scrollWidth`/`clientWidth` (via a `scroll` listener + `ResizeObserver`) and renders nothing when there's nothing to scroll. Unlike `ScrollArrows`, it sits in normal document flow directly below the scrollable element (`margin-top`, reserving real layout height) rather than floating over the diagram — it needs no `position: relative` host wrapper of its own, so no extra div is required around it; just render it as a sibling right after the scrolling `<figure>`/`<div>` and before `<MidiInstrumentChrome>`. Never wrap `AlphaTabPlayer`'s own scroll containers (`.player-frame`, `.compact-player-frame`, `.alphatab-container`, `.figure-tab`, `.tab-panel`) with `HorizontalScrollbar` — it manages its own horizontal scrolling internally and must not be touched externally (see the AlphaTab scrollbar rule above). The scrollable element itself (the one holding `ref={scrollRef}`) must also hide its own native scrollbar — `scrollbar-width: none;` plus a sibling `&::-webkit-scrollbar { display: none; }` rule — or the page shows both the native bar and `HorizontalScrollbar` stacked on top of each other, wasting vertical space for a control that's now redundant everywhere it's applied (`.fretboard-wrap`, `.fretboard-figure`, `.scale-board-wrap`, `.position-scroll`, `.pentatonic-board-wrap`, `.blues-map-wrap`).
- Every guitar fretboard (not `MiniKeyboard` — this feature is neck-specific) has a note-marking "paint" mode: a circular color-palette toggle button, rendered via `<PaletteToggleButton active={paintMode} onClick={...} />` from `@/app/components/guitar/NoteMarksOverlay`, placed as the *first* child inside `<MidiInstrumentChrome>` — to the left of the KB button, changing the children row's fixed order from "KB, volume, metronome" to "palette, KB, volume, metronome". `paintMode` is `useState(false)` like `kbMode`; marks themselves live in `const { marks, toggleMark } = useNoteMarks()` from `@/app/lib/useNoteMarks` (`marks: Record<noteName, hexColor>`). While `paintMode` is on, every new note press — `onPointerDown` and the keyboard `down()` handler alike — calls `toggleMark(noteName)` in addition to (never instead of) its normal `playNote`/`switchNote` call: first press of a note assigns it an unused color from a fixed 12-color palette (one per possible pitch class, so two simultaneously marked notes never collide) and lights up *every* occurrence of that pitch class anywhere on the neck (all strings, all octaves, all frets between the diagram's own `startFret`/`endFret` — not just the pressed one); pressing a note that's already marked removes only that note's color, leaving every other marked note untouched. Marks persist even after `paintMode` is switched off — the toggle only gates whether *new* presses add or remove marks, it does not hide or clear existing ones. Because `kbMode`'s keyboard `down()`/`up()` live inside a `useEffect` keyed on `[kbMode, kbRange]`, reading `paintMode` there directly would close over a stale value the moment the effect stops re-running on every paint-mode toggle — so every file also keeps a `paintModeRef` synced via its own `useEffect(() => { paintModeRef.current = paintMode; }, [paintMode])` and reads `paintModeRef.current` inside `down()` (exactly the same reason `volumeRef` exists next to `volume`). Rendering is `<NoteMarksOverlay marks={marks} startFret={...} endFret={...} getX={...} getY={...} getNoteName={...} />` placed inside the `<svg>`, right before `{interactionOverlay()}`; it iterates every (string, fret) in range and draws a colored circle + note-name label (matching the fretboard's own note-dot look) wherever `getNoteName(string, fret)` matches a key in `marks`. `getNoteName` just wraps whatever note-name helper already exists in that file — `noteNameForFret(string, fret)` directly where that's the local shape (`ReducedFretboardDiagram`, `FigurasAcordesPage`, `NotacionMusicalPage`), or `(string, fret) => noteNameForFret(stringTunings[string - 1].open, fret)` where `noteNameForFret` takes a pitch class instead (`AcordesSeptimaPage`, `EscalaCompletaSolMayorPage`, `PentatonicaPage`, `AcordesEscalaSolMayorPage`) — never introduce a third shape. `PentatonicaBluesPage` additionally wraps every call (both the `toggleMark` calls and `getNoteName`) in its existing `displayNote()` so the mark's key/label reads "Bb" instead of "A#", matching how that page already labels the blue note everywhere else. `AcordesEscalaSolMayorPage` is again the one exception: since its 7 small `ChordScaleFretboard` cards already share one `kbMode`/`volumeRef`/controls bar via props, `paintMode`/`marks`/`toggleMark` are lifted to the parent the same way and passed down as three more props, so marking a note on any one card lights it up on all 7 simultaneously and the palette button lives once in the shared bar, not per card.

- Fretboard "practice exercise" mode (first used on `/lecciones/temario/tablaturas`, meant to be reused on more necks): `useFretboardPractice(exercises)` from `@/app/lib/useFretboardPractice` + `PracticeButtons` / `PracticeTargetMarker` / `PracticeFeedback` / `FretboardPracticeStyles` from `@/app/components/guitar/FretboardPractice`. `ReducedFretboardDiagram` already wires it behind the optional `practiceExercises` prop (`{ label, notes: { string, fret }[] }[]`) — pass that instead of re-implementing. To add it to another fretboard, call `registerNote({ string, fret, kind, from? })` exactly where that file already decides a note SOUNDS (right before its `playNote`/`switchNote` await): `'pluck'` (new press), `'hammer'` (higher fret on a sounding string — tapping counts), `'pulloff'` (release falls back to a lower held fret), `'slide'` (pointer drag, with `from` = previous position).
